# Maze Generator & Solver

This project is a Java Swing application that creates a random maze and then solves it. I used Depth-First Search (DFS) with the Stack from our labs to generate the maze, and Breadth-First Search (BFS) with the Queue from our labs to solve it.

Both algorithms are animated, so you can see the maze being created and then watch the solver find its way to the exit.

## How to compile and run

You will need JDK 11 or newer.

```bash
cd src
javac *.java
java MazeApp
```

To run the tests without opening the application:

```bash
cd src
java MazeTest
```

## How to use the app

- Choose the number of **Rows** and **Cols** (between 1 and 150). It starts at 20 x 20 by default.
- Press **Generate** to start creating a random maze.
- When the maze is finished, press **Solve** to watch BFS find a path to the exit.
- Use the **Speed** slider to change how fast everything runs. Moving it to the right makes the animation faster because it completes more steps at a time.

### Colours

| Colour | Meaning |
|---|---|
| Dark purple | Cells that haven't been visited yet |
| White | Open paths in the maze |
| Bright violet | Cell currently being worked on |
| Light lavender | Cells BFS has already explored |
| Crimson | Final path to the exit |
| Deep purple / dark crimson | Start (top-left) / exit (bottom-right) |

## Classes used

Here is a an explanation of what each class does:

- `Cell` - Represents one square in the maze. It stores the row and column, four walls and whether the cell has been visited.
- `Maze` - Holds all the cells in a 2D array (`Cell[rows][cols]`). It also has methods for getting neighbours, removing walls and checking if movement is possible.
- `StackInterface`, `StackReferenceBased`, `StackException`, `Node` - My stack implementation from Lab 3.
- `QueueInterface`, `QueueArrayBased`, `QueueException` - The queue classes from our queue lab.
- `MazeGenerator` - Creates the maze using DFS and the stack.
- `MazeSolver` - Uses BFS and the queue to solve the maze. It also has a parent array to remember where each cell came from so it can build the final path.
- `MazePanel` - Draws the maze on the screen using `JPanel`.
- `MazeApp` - Sets up the main window, buttons, controls and animation.
- `MazeTest` - Tests the generator and solver on different maze sizes without opening the GUI.

## Design choices

### Using the Stack and Queue from the labs

I decided to use the Stack and Queue I made in the labs since it was in the projects requirements.

The lab classes store everything as an `Object`, so when I get a cell back from the stack or queue, I need to cast it back to a `Cell` using `(Cell)`.

The queue has a fixed size of 50. This worked for all my tests, including the larger 150 x 150 maze.

### Grid coordinates

I store the maze using `grid[row][col]`.

The first cell is at (0,0), which is the top-left corner. Rows increase as you go down and columns increase as you go right. This works well with Swing because it also draws from the top-left corner.

I use these calculations when drawing each cell:

```java
x = col * size;
y = row * size;
```

### Handling the edges

The `getCell(r, c)` method returns `null` if the position is outside the maze.

This means I don't need to write separate code for corner cells or edge cells. When finding neighbours, I just skip any that return `null`. This also stops the generator from removing the outside walls.

### Removing walls

Each wall belongs to two cells. For example, if two cells are beside each other, the right wall of the first cell is also the left wall of the second cell.

To make sure both walls are updated together, I use the `removeWallBetween()` method. This stops the walls from getting out of sync. The `canMove()` method checks if there is an open passage between cells.

### Animating the algorithms

I added a `step()` method to both the generator and solver. This lets the application run the algorithms one step at a time so they can be animated.

I used a `javax.swing.Timer` to keep calling the step methods. I didn't use `Thread.sleep()` because that would freeze the window while the maze is running.

I also added `generateAll()` and `solveAll()` methods. These run the algorithms completely without animation, which makes it easier to test them.

### Why I used BFS

I used BFS because it explores the maze one level at a time, starting from the beginning.

When BFS reaches the exit, it has found the shortest path. The mazes generated by my program are perfect mazes, which means there is only one possible path between any two cells. However, BFS would still find the shortest path if the maze had loops or more than one possible route.

## Algorithms

### Generator: DFS using a Stack

The generator starts with all the walls in place. It then starts at the top-left cell and randomly chooses an unvisited neighbour to move to. When it moves to a new cell, it removes the wall between the two cells and marks the new cell as visited.

If it gets stuck and has no unvisited neighbours left, it goes back to the previous cell using the stack. It keeps doing this until every cell has been visited.

```text
SETUP:
    mark all cells as unvisited
    mark start as visited
    push start onto stack

STEP:
    if stack is empty:
        finished = true
        return false

    current = stack.peek()
    find unvisited neighbours of current

    if there are no unvisited neighbours:
        pop stack
    else:
        randomly choose a neighbour
        remove the wall between the cells
        mark neighbour as visited
        push neighbour onto stack

    return true
```

I used a stack instead of recursion to keep track of where the generator has been. Each cell is only visited once, and walls are only removed when moving to a new cell. This creates a perfect maze with no loops, where every cell can be reached.

### Solver: BFS using a Queue

The solver starts at the top-left cell and uses BFS to search for the exit at the bottom-right. It uses a queue to keep track of which cells need to be checked next.

It checks the cells in order, looking at all the possible open neighbours. If a neighbour hasn't been visited, it marks it as visited, saves where it came from and adds it to the queue.

When it reaches the exit, it uses the parent array to work backwards and find the path from the start to the exit.

```text
SETUP:
    mark all cells as unvisited
    mark start as visited
    add start to queue

STEP:
    if finished:
        return false

    if queue is empty:
        finished = true
        return false

    current = remove cell from queue

    if current is the exit:
        found = true
        finished = true
        buildPath()
        return false

    for each neighbour of current:
        if there is no wall and neighbour is unvisited:
            mark neighbour as visited
            save current as its parent
            add neighbour to queue

    return true

BUILDPATH:
    start at the exit
    follow the parent cells back to the start
    add each cell to the path
    reverse the path so it goes start to exit
```

I mark cells as visited when I add them to the queue. This stops the same cell from being added more than once.

I used BFS because it checks cells in order of distance from the start, so it finds the shortest path to the exit.

## Testing

I made a separate `MazeTest` class to check that everything works properly. I tested different maze sizes, including very small mazes and a much larger 150 x 150 maze.

The sizes I tested were:

- 1 x 1
- 1 x 10
- 10 x 1
- 2 x 2
- 10 x 10
- 30 x 30
- 50 x 80
- 150 x 150

For each maze, I checked the following:

1. Every cell is visited by the generator.
2. The number of open passages is `rows * cols - 1`, which checks that there are no loops.
3. BFS is able to find a path from the start to the exit.
4. The path starts at the top-left cell and finishes at the bottom-right cell.
5. The path doesn't go through any walls.

All 56 tests have passed.
